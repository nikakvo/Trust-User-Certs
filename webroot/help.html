1 · what this module does

Android keeps CA certificates in two stores. The system store is trusted by every app. The user store — where a certificate goes when you install it in Settings — is ignored by almost every app since Android 7, unless the app opts in.

That makes HTTPS inspection tools (HttpCanary, mitmproxy, Burp, Charles…) useless for most apps: you install their CA, and apps still refuse the connection. This module copies your user certificates into the system trust store, so every app trusts them as if they came with the system.

Install and remove certificates the normal way, in Android Settings. With Live Sync on, the change reaches the system store within a few seconds — no reboot.
Tested on a Poco F6 Pro with the Xiaomi.eu ROM (HyperOS 3, Android 16) and SukiSU-Ultra only. The Android 7–13 path and other devices, ROMs and root managers are supported by design but have not been tested by the author. If something does not work on your device, the service log usually says why.
A certificate in the system store makes every app trust whoever holds its private key. Only install CAs you created yourself or fully trust, and remove them when you are done.
2 · installing a certificate

In Android Settings

  1. Copy the certificate file to the phone, e.g. to Download.
  2. Open Install a certificate. The menu path differs between ROMs — the Settings search for CA certificate usually finds it.
  3. Choose CA certificate, confirm the warning, pick the file.

On the Xiaomi.eu ROM (HyperOS 3) the path is:

Settings
 → Fingerprint, face data, and screen lock
 → Privacy
 → More security settings
 → Encryption & credentials
 → Install a certificate
 → CA certificate

HyperOS asks for your screen-lock password when you open the lock-screen settings, and for your fingerprint before the file picker opens.

Android stores it in /data/misc/user/0/cacerts-added, Live Sync copies it into the system store, and the certificate list in this interface shows it as trusted. Android may ask you to set a screen lock first.

To remove it: Encryption & credentials → Trusted credentials → User → the certificate → Remove. Live Sync takes it out of the system store as well.

The three options in "Install a certificate"

  • CA certificate — a certificate authority your phone should trust. This is the one proxy and inspection tools need, and the only one this module works with.
  • VPN & app user certificate — a key and certificate that identify your phone to a server: VPN login, apps using client certificates. It does not make anything trusted.
  • Certificate — called Wi-Fi certificate on most ROMs: credentials for enterprise Wi-Fi (802.1X / EAP). Not related to this module.

Trusted credentials vs. User credentials

Trusted credentials → User lists the CA certificates in the user store — exactly what this module reads. User credentials lists keys and certificates in Android's keystore ("Installed for VPN and apps"): client certificates, keys created by apps, and on some ROMs copies of installed CAs. Nothing there is trusted for HTTPS, and the module neither reads nor changes it.

Proxy apps such as HttpCanary do not need a VPN certificate: their "VPN" is a local VpnService that routes traffic through the app, and decrypting HTTPS depends only on their CA certificate being trusted.

File formats

extensionwhat it is
.crt .cer .pem .derAn X.509 certificate, as text (PEM) or binary (DER). This is what you want. Install it as CA certificate.
.p12 .pfxA PKCS#12 bundle: certificate and private key. It is not a CA certificate — Android offers it as a VPN / app or Wi-Fi certificate. Extract the certificate first (below).
# Termux: pkg install openssl-tool
openssl pkcs12 -in file.p12 -nokeys -out ca.pem
Proxy apps often offer their own "install to system" option with root. Use the Settings installer instead: this module then manages the certificate, and removing it in Settings removes it everywhere.
3 · custom certificates

Certificates you do not want in Android's user store can be dropped straight into the module's own directory:

/data/adb/trust-user-certs/certs/

They are added to the system store on every boot and every sync, exactly like user certificates, and appear in Settings under System. The directory is root-only (0700) on purpose: whoever can write to it can make the whole phone trust a CA. Live Sync watches it too, so a new file is picked up within seconds.

The file name matters

Android finds certificates by the hash of their subject, so the file must be named <subject_hash_old>.0, e.g. 87bc3517.0. Any other name is copied but ignored by Android; the log warns about it. PEM and DER content both work.

openssl x509 -in ca.pem -noout -subject_hash_old
# 87bc3517  ->  name the file 87bc3517.0

Easiest way, without openssl

Install the certificate once in Settings — Android names the file correctly — then copy it over and, if you like, remove it from Settings:

su -c "cp /data/misc/user/0/cacerts-added/87bc3517.0 /data/adb/trust-user-certs/certs/"
su -c "chmod 644 /data/adb/trust-user-certs/certs/87bc3517.0"

The certificate list shows it with a custom tag, and the header chip counts it.

Uninstalling the module deletes /data/adb/trust-user-certs, including this directory. Keep a copy of your custom certificates somewhere else. Updating the module keeps them.
An app that checks whether "its" certificate is installed may only look at the user store and warn that it is missing — even though every app trusts the certificate through the system store.
4 · how the injection works

The module never modifies /system. It mounts a merged copy of the trust store over the real one. The copy is rebuilt from scratch each time:

  1. base_certs — a snapshot of the stock system store, taken while no overlay of the module is active;
  2. plus your user certificates and your custom certificates;
  3. minus anything matched by an exclusion rule.

Because the set is always rebuilt from the stock snapshot, a certificate you remove disappears from the system store too.

Android 14 and newer

The trust store lives in the Conscrypt APEX (/apex/com.android.conscrypt/cacerts). It cannot be mounted over this early in boot, so post-fs-data.sh only marks the work as deferred; service.sh waits for zygote, then bind-mounts the merged set over the APEX path and into the mount namespaces of init and zygote with nsenter.

Android 13 and older

A tmpfs holding the merged set is mounted over /system/etc/security/cacerts at post-fs-data, before any app starts.

Verification

Every inject and sync is checked against the live store: the store must hold at least the staged set, and every user and custom certificate must actually be there. The result is INJECT_OK and a log line such as:

Verify OK — 151 certs live, 1/1 user certs trusted, 1/1 custom certs trusted

A mount that silently failed is reported as a failure, never as a success.

Apps that were already running when a certificate was added may keep their old trust cache until they are restarted.
5 · live sync

Live Sync keeps the system store in step with your certificates while the phone runs. It uses the root manager's own busybox inotifyd — Magisk, KernelSU, SukiSU and APatch all ship it — so the kernel reports every change and nothing is polled.

What is watched

  • /data/misc/user/0/cacerts-added — certificates installed or removed in Settings
  • /data/misc/user/0 — notices cacerts-added being created (your first certificate ever) or removed
  • /data/adb/trust-user-certs/certs — your custom certificates

Only writes, creations, deletions and renames count. Reading the certificates — which the module itself does on every sync — never triggers a sync.

One sync per change

Installing a certificate produces a short burst of events (create, then write). The watcher waits until the directory has been quiet for 2 seconds and then syncs once; if changes never stop, it syncs anyway after 10 seconds. The log shows each burst:

Change detected (2 event(s), first: n cacerts-added/87bc3517.0)

Self-healing

The watcher checks every 60 seconds that inotifyd is still running, restarts it if not and syncs once to catch anything missed. If it fails more than 5 times within 10 minutes — or inotifyd is not available at all — Live Sync switches to polling every 30 seconds. Both modes are shown in the Live Sync card.

When idle, Live Sync is two sleeping processes — the watcher and its inotifyd — and uses no CPU.

Turned off

With Live Sync off, certificates are still injected at every boot; changes just wait for the next reboot or for Force Inject.

6 · boot-loop protection

Mounting over the trust store happens early in boot, so a failure must never leave the phone stuck in a boot loop.

  • Every boot increments a fail counter in post-fs-data.
  • The counter is reset only once Android reports sys.boot_completed — a boot that really finished.
  • After 3 boots that did not finish, injection is disabled and the status shows BLOCKED. The phone boots with the stock trust store.

Once you have found the cause, press Reset Fail Counter and reboot.

7 · exclusion rules

Certificates matched by a rule are kept out of the system store, even if they are installed.

fileone rule per line
exclude_hashesa subject hash — the file name without .0
exclude_subjectstext matched against the certificate body (user and custom certificates only)

Both live in /data/adb/trust-user-certs/; lines starting with # are comments. They ship with a rule for AdGuard's personal intermediate CA, which conflicts when it sits in the system store. An excluded certificate is labelled excluded by rule in the list and does not count as a failure.

8 · the interface

Status

statemeaning
WORKINGthe overlay is active and every user and custom certificate is in it
READYthe overlay is active; you have no certificates installed yet
PARTIALthe overlay is active but at least one certificate is missing from it
NOT WORKINGthe trust store is not overlaid
BLOCKEDthe boot-loop guard stopped the injection

The chips show the number of certificates in the live store, trusted user certificates, trusted custom certificates (when you have any) and the fail counter. An +1x suffix counts certificates dropped by an exclusion rule.

Certificates

Every user and custom certificate with its subject, validity, serial, source and whether it actually reached the system store.

Live Sync

One tap starts or stops the watcher. The card shows the mode (event-driven or polling), the PID, how many syncs ran and when the last one was.

Actions

buttonwhat it does
Force Injectrebuilds the merged set and refreshes the overlay; rebuilds the overlay from scratch if verification fails
Force Syncone Live Sync pass; also restarts the watcher if Live Sync is on but the watcher is gone
Reset Fail Counterclears the boot-loop guard

Log

Filterable by INFO / WARN / ERR / DBG. Log level 0 records errors only, 1 is normal, 2 adds debug detail.

9 · command line

The interface runs these same commands, so everything works from a root shell as well:

S=/data/adb/modules/trust-user-certs/service.sh

sh $S --status              # key=value status dump
sh $S --certs               # user/custom certificates, base64
sh $S --log 200             # tail of the service log
sh $S --clear-log
sh $S --force-inject
sh $S --sync                # one Live Sync pass
sh $S --watch-start
sh $S --watch-stop
sh $S --config LIVE_SYNC 1  # also starts / stops the watcher
sh $S --config LOG_LEVEL 2
sh $S --reset-fail

Quick health check:

su -c "sh $S --status" | grep -E 'INJECT_OK|WATCH|USER_|CUSTOM_'
10 · troubleshooting

NOT WORKING

The overlay is not mounted, usually because a bind mount failed. Look for Verify FAILED in the log and press Force Inject.

PARTIAL

A certificate did not reach the store. The certificate list marks which one. A custom certificate with a wrong file name is the usual cause (see section 3).

BLOCKED

Three boots in a row did not finish. Find the cause in the log, then press Reset Fail Counter, or:

su -c "echo 0 > /data/adb/trust-user-certs/boot_fail_count"

Live Sync shows DEAD

Press Force Sync — it restarts the watcher — or toggle Live Sync off and on. A watcher started from here moves itself out of the manager app's cgroups, so closing the manager does not kill it.

Live Sync says "polling every 30s"

inotifyd is missing from your root manager's busybox or kept exiting. Syncing still works, only up to 30 seconds later. The log says which of the two happened.

Android will not install my certificate

A .p12 / .pfx file is not a CA certificate — extract it first (section 2). Versions up to v3.1 created cacerts-added as root, which could stop Android from adding the first certificate; since v4 the module repairs that at install and at boot.

One app still rejects the certificate

That app uses certificate pinning: it trusts only specific certificates, no matter what is in the system store. No trust-store module can change that; a pinning bypass such as JustTrustMePro (LSPosed) can.

"nsenter is unavailable" in the log

The certificates cannot be pushed into the zygote mount namespace, so apps started before the injection may only see them after a reboot. --status lists the tools that were found.

Interface is blank or shows a red box

Your root manager did not provide a working ksu JavaScript bridge. Open the module through KernelSU, SukiSU, APatch or MMRL. Plain Magisk has no WebUI; the module itself still works there.

11 · uninstall

Removing the module in your root manager takes effect at the next reboot: the overlay is no longer mounted, so the stock trust store is back, and uninstall.sh stops anything left of Live Sync and deletes /data/adb/trust-user-certs.

That includes your custom certificates. Back them up first.

Certificates you installed in Android Settings are not touched: they stay in the user store, where only apps that opt in trust them.

12 · file layout
/data/adb/modules/trust-user-certs/
├── post-fs-data.sh    early boot: inject (≤13) or defer (≥14)
├── service.sh         boot flow, Live Sync, command interface
├── sh/common.sh       paths, logging, locks, tools
├── sh/inject.sh       staging, mounting, verification
├── customize.sh       installer
├── uninstall.sh       cleanup, unmount
└── webroot/           this interface

/data/adb/trust-user-certs/     (mode 0700, survives updates)
├── config             LIVE_SYNC, LOG_LEVEL
├── stats              runtime state and counters
├── boot_fail_count    boot-loop guard
├── certs/             your custom certificates
├── base_certs/        snapshot of the stock store
├── cert_stage/        the merged set that is mounted
├── exclude_hashes
├── exclude_subjects
├── locks/
├── logs/service.log   rotates at 256 KB
├── watcher.pid        runtime only, cleared on boot
├── inotifyd.pid       runtime only
└── watch.fifo         inotifyd → watcher

/data/misc/user/0/cacerts-added/   Android's user store (owned by system)

Nothing mutable lives in the module directory, because a module update replaces it wholesale.
